# Спецификация продукта

Draft 0.1 · 2026-10-18. Название, порядок платформ, три протокола первой версии и два репозитория выбраны владельцем. Остальные детали ниже — предлагаемая базовая спецификация, не одобренная реализация.

## Пользовательский результат

Принятое уточнение владельца от 2026-10-18: **Beamer 4 — основной продуктовый ориентир**. Повод — платность приложения; цель — самостоятельно с помощью AI-agents создать аналог для своих задач и освоить его разработку. Успех проекта определяется полезностью и удобством собственного приложения, а не обязательным доказательством уникальности на рынке. Лицензия и условия распространения собственного продукта пока не выбраны.

Пользователь выбирает локальное видео и телевизор/приставку; приложение готовит совместимый вариант и управляет воспроизведением. Интернет-сервис и AI API не являются обязательной частью приложения. Зависимость конкретного приёмника от внешних сервисов учитывается отдельно.

### Как используем ориентир

На [официальной странице Beamer 4](https://softorino.com/beamer) заявлены drag-and-drop, автоматическая подготовка видео, Apple TV/Cast, субтитры, управление и очередь. Это заявленные возможности продукта, не результаты нашего сравнительного испытания.

| Сценарий собственного приложения | Место в плане |
|---|---|
| Добавить видео выбором файла или перетаскиванием, выбрать телевизор, начать просмотр | M1, REQ-001/002/006 |
| Приложение само выбирает direct/remux/transcode, пользователь не конвертирует файл вручную | E09, REQ-004/005; M1 начинает с совместимого клипа |
| Управлять воспроизведением из приложения | M1, REQ-006/007; управление аппаратным пультом — отдельный проверяемый сценарий |
| Выбирать дорожки, использовать субтитры и очередь | После стабильного playback/E09; детали E10 остаются Draft |
| Использовать Sony DLNA и затем Linux/Windows/Android | Уже выбранные расширения Open Media Cast |

Полное совпадение всех возможностей Beamer не является критерием первого среза. Первый smoke и M1 приближают к этому ориентиру; дальнейший объём выбирается по повседневным сценариям владельца. Маркетинговое «любой формат» заменяется проверяемой матрицей входных файлов и приёмников.

## Платформы и границы

1. macOS 14 и новее, ARM64, без Intel-сборки.
2. Fedora 44/45 Xfce — целевой диапазон, уточнённый в review; фактически установленная версия, CPU/GPU и архитектура стенда ещё требуют записи.
3. Windows 10 и 11: версии и архитектуры фиксируются до реализации порта.
4. Android: самостоятельный отправитель файлов телефона, а не только пульт Mac; minSdk/ABI и устройства уточняются до принятия соответствующей фазы.

Первый macOS-релиз включает AirPlay (с приоритетом Apple TV 3), Google Cast и DLNA DMR. Это не обещание поддержки всех телевизоров или новых Apple TV без тестирования. Квалификация выполняется по моделям и прошивкам.

Первая квалификация AirPlay ограничена legacy-видеосценарием Apple TV 3. AirPlay 2 — отдельный профиль/adaptor, пока вне квалификации v1. Для Cast с Default Media Receiver закладывается доступ приёмника в интернет; автономная работа без WAN не обещается. На 2026-10-18 владелец подтвердил отсутствие Cast-стенда: ближайший smoke охватывает Apple TV и Sony, gate полного v1 остаётся открытым.

Предлагаемые non-goals v1: mirroring экрана, DRM-контент, захват произвольного браузера, собственный receiver, управление роутером, cloud account, синхронный multiroom, загрузка видео с сайтов, каталогизация всех дисков. Изменение non-goals требует решения владельца.

## Требования и приёмка

| ID | Требование | Наблюдаемый критерий |
|---|---|---|
| REQ-001 | Локальный выбор файла | Выбор через диалог или drag-and-drop приводит к одному потоку подготовки; соседние каталоги не индексируются; отмена выбора не создаёт сеанс |
| REQ-002 | Обнаружение приёмников | AirPlay/Cast через применимый discovery, DLNA через SSDP; ошибки разрешений отличимы от пустого списка; macOS 15+ Local Network проверяется из собранного .app отдельно от CLI |
| REQ-003 | Сопряжение | Если требуется, используется штатный PIN/доступ; неверный код даёт понятную ошибку; секреты не попадают в логи |
| REQ-004 | Выбор media profile | По метаданным и capabilities определяется direct/remux/transcode; неизвестный формат не выдаётся за поддержанный |
| REQ-005 | Доставка выбранного медиа | Session URL выдаёт только выбранное медиа; законченный файл поддерживает Range; DLNA metadata/protocolInfo и HTTP contentFeatures/transferMode согласованы с фактическим seek и преобразованием |
| REQ-006 | Основное воспроизведение | На квалифицированном устройстве start/pause/resume/seek/stop проверены отдельно; незадокументированные ограничения не скрываются |
| REQ-007 | Честное состояние | UI различает preparation, connecting, playing, paused, failed, ended; таймаут команды не превращается в ложный success |
| REQ-008 | Отмена и очистка | Stop/cancel завершают подготовку, освобождают файлы/процессы/сервер и удаляют временные данные по политике |
| REQ-009 | Сеть и восстановление | Потеря Wi-Fi/receiver не вызывает бесконечных retry; восстановление требует подтверждённого состояния; старые события не меняют новую сессию |
| REQ-010 | Дорожки видео и субтитры после M1 | M1: один совместимый видеоклип со звуком, без внешних субтитров. После E09: SRT UTF-8 → WebVTT для выбранного Cast-профиля; burn-in как проверяемый fallback для legacy/DLNA; синхронность после seek |
| REQ-011 | Ограничение ресурсов | Настраиваемый лимит cache, один активный transcode в базовом режиме; disk-full и отказ кодека завершаются управляемой ошибкой |
| REQ-012 | Приватность | Файлы не отправляются в облако; pairing credentials защищены; экспорт диагностики очищен от пользовательских данных |
| REQ-013 | Установка | Собранный пакет запускается на целевой ОС без среды разработчика; обязательные зависимости включены или явно объявлены |
| REQ-014 | Доступный UI | Основные действия доступны клавиатурой на desktop; название/состояние элементов читаемы; на Android учитывать screen reader и масштаб текста |
| REQ-015 | Независимость платформ | Общие domain/contract tests работают без UI конкретной ОС; платформенные адаптеры проходят собственные smoke tests |

REQ-010 и объём очереди остаются Draft: одиночный активный файл, затем небольшая последовательная очередь. Burn-in требует перекодирования видео; необходимость на конкретном Sony/Apple TV ещё проверяется. Cast не ограничен WebVTT: официальный список также включает TTML и CEA-608/708; WebVTT здесь выбран как стартовый путь, см. [Cast media](https://developers.google.com/cast/docs/media).

Самостоятельные аудиофайлы пока не определены: звук видеодорожки входит в M1, audio-only через URL и RAOP на колонки — разные дополнительные сценарии. Их включение в v1 требует решения владельца, а не молчаливого расширения REQ-010.

## Состояния сессии

`Idle → Inspecting → Preparing (если нужно) → Connecting → Playing ↔ Paused → Ended`.

Из активных состояний возможны `Stopping → Idle` и `Failed`. Pairing — явный подэтап подключения, а не повторяющееся окно без лимита. Каждая сессия имеет ID; события с другим ID игнорируются. После restart приложения незавершённые cache/jobs распознаются и очищаются; автоматический запуск фильма без действия пользователя не предусмотрен.

## Проверяемые ориентиры — на согласование

Базовый клип: синтетический 720p H.264/AAC, 30 fps, duration 120 s. Для него предлагаются discovery ≤15 s в исправной LAN, first frame ≤10 s при direct play, ответ UI на stop ≤1 s, освобождение ресурсов ≤5 s. Это целевые пределы для измерения, не обещания текущей реализации. Сеть, bitrate, кодек и модель приёмника записываются рядом с измерением.

Для qualify: 30 минут непрерывного воспроизведения, pause/resume, seek вперёд и назад, stop, потеря сети, повторный запуск. Для transcode отдельно измерять подготовку и скорость обработки; не обещать realtime для любого файла. Более тяжёлые fixtures вводить по одному параметру, фиксируя исходные настройки.

## Реальные устройства и неизвестное

Есть Mac mini M4, Apple TV 3, Sony KDL-48W605B, Nothing Phone (1), смартфоны семейства Xiaomi/Redmi/Poco. Точные ОС/прошивки не зафиксированы. Системный AirPlay работает по сообщению владельца; это не evidence нашего sender. Cast-приёмник не указан. [Матрица](../testing/DEVICE_MATRIX.md) сохраняет эти пробелы.
