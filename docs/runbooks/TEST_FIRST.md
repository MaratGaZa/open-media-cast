# Первые тесты и порядок разработки

2026-10-19. Требование владельца: тесты до основной реализации; тесты и GitHub
Actions — первые отдельные задачи через issue, ветку, review и PR.

## Test-first для каждого нового поведения

1. Выбрать одну небольшую задачу и критерий из SPEC/TEST_STRATEGY.
2. Написать тест публичного поведения и запустить его. Зафиксировать RED:
   ожидаемое падение именно из-за отсутствующего поведения, а не ошибки окружения.
3. Написать минимальную реализацию. Получить GREEN; повторить затронутую регрессию.
4. При необходимости упростить код, сохранив зелёные проверки.
5. Commit/push → review актуального SHA → PR → исправления и повторное review →
   approve → merge. Не объединять намеренно красный тест в main отдельно от
   реализации. Следующий зависимый шаг начинается после merge предыдущего.

Сначала покрывается конкретный небольшой контракт, а не весь ещё не написанный
продукт. Для существующего кода регрессионные тесты могут сразу пройти: тогда
отдельно проверить их чувствительность намеренной ошибкой во временной копии.
Не называть это историей RED/GREEN первоначальной реализации. Для текстовой
правки не придумывать unit-тест наличия заголовка. Самопроверка не заменяет
независимое review и approve.

## T01 — проверяемый HTTP-эталон

[Issue #1](https://github.com/MaratGaZa/open-media-cast/issues/1).
`tools/protocol-lab/media_server.py` — существующий исследовательский сервер
E00.6, перенесённый без изменения поведения. Это не продуктовый backend.
`test_media_server.py` запускает собственный процесс только на `127.0.0.1`,
создаёт временные синтетические байты и закрывает процесс после каждого теста.
Эти байты проверяют HTTP, не являются MP4-клипом и не проверяют кодеки.

На Python 3.13 с установленной зависимостью:

```sh
python -m pip install -r tools/protocol-lab/requirements-tests.txt
python -m unittest discover -s tools/protocol-lab -p 'test_media_server.py' -v
```

Использовать отдельную тестовую среду либо уже подготовленную лабораторную.
В первой задаче закреплена прямая зависимость; фиксация окружения CI — T02.

Проверки: GET с точными байтами и длиной; HEAD без тела; bounded/open-ended/suffix
Range и диапазон за концом файла (206 с точным Content-Range, длиной и байтами);
полностью недостижимый диапазон (416); неверный токен/корень/чужой путь (404);
POST (405); корректный выход процесса, cleanup marker и недоступный listener.
Это части TEST-HTTP-01/02 уровня E2. Активное revoke, параллельная выдача,
session mismatch, codec probe и физические телевизоры здесь не проверяются.

Будущий Rust-сервер должен получить собственные тесты **до реализации** с теми
же проверками ответов плюс дополнительные требования задачи. Успех этого
Python-эталона не закрывает приёмку Rust и не принимает Proposed ADR-003.

## T02 — автоматизация после T01

[Issue #2](https://github.com/MaratGaZa/open-media-cast/issues/2) зависит от merge
T01. В отдельной ветке от обновлённого main добавить согласованный
`.github/workflows/ci.yml`: тесты на открытии/обновлении PR и push в main после
merge. Закрепить Actions, read-only permissions и timeout. Проверить реальный
PR-run, получить review/approve и после merge проверить отдельный main-run.
Не сообщать о работающем CI, пока этих запусков нет. Облачные тесты не обращаются
к домашним устройствам. После появления Rust добавить его проверки до основной
реализации; отсутствие workspace не является успешным cargo test.

События workflow: [документация GitHub](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows).
