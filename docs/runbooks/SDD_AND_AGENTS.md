# Spec-Driven Development и работа AI-agents

Draft 0.1 · 2026-10-18. [SPEC](../specs/PRODUCT_SPEC.md), [очередь](../plans/IMPLEMENTATION_PLAN.md), [AGENTS](../../AGENTS.md).

## Рабочий цикл

1. Владелец описывает пользовательский результат. Агент уточняет только сведения, которые меняют решение; независимую работу продолжает.
2. Агент связывает задачу с REQ, формулирует наблюдаемый тест и предлагает изменение SPEC, если контракт меняется. Труднообратимый выбор оформляет Proposed ADR с альтернативами.
3. Владелец принимает нужный объём. Принятие документов не разрешает все последующие задачи сразу.
4. Исполнитель делает одну задачу очереди в изолированной ветке. Перед началом проверяет корень репозитория и несвязанные изменения.
5. Выполняются проверки минимально достаточного уровня. Протокольные mocks проверяют наш код, но не поведение телевизора.
6. Review проверяет требования, ошибки, resources/lifetime, privacy и реальное evidence. Независимый reviewer желателен для протоколов/пакетов, но не является выполненным review до получения его отчёта.
7. Исправления проходят повторные затронутые проверки. Владелец получает отчёт: что работает, что не проверено, что делать дальше.
8. Commit/PR/release выполняются только в ранее разрешённом объёме. Следующая задача не начинается автоматически вне поручения.

## Роли и границы

Владелец принимает продуктовые решения и наблюдает реальное устройство. Исследователь проверяет источники и формулирует гипотезы. Исполнитель меняет код. Reviewer оценивает конкретный diff/snapshot. Автор учебного материала объясняет уже проверенный результат и явно обозначает ещё не реализованные примеры.

Это роли в процессе, не требование держать четыре платных агента постоянно. Можно использовать одну модель последовательно; для независимого review дать другой модели/сессии raw diff, требования и результаты без подсказки желаемого вывода. Параллельные изменения допустимы в независимых write scopes с заранее определённой интеграцией.

## Пакет входа агенту

```text
Задача: E03 — проверить AirPlay на Apple TV 3.
Прочитай AGENTS.md, REQ-002/003/006 и RECEIVER_SPIKES.md.
Цель: измерить реальное поведение синтетического клипа.
Сначала проверь готовность E02 и разрешённый доступ к устройству.
Не меняй режим безопасности для получения успешного результата.
Сохрани версии, результаты каждой команды и незакрытые вопросы.
Не реализуй GUI, не публикуй и не переходи к следующему протоколу.
```

Это пример будущей задачи, не команда выполнить её сейчас. Для других задач сохраняется конкретность входа, границ и evidence; текст не нужно копировать механически.

## Передача контекста

Summary содержит: принятое решение, текущее состояние, SHA/snapshot, сделанные файлы, пройденные/непройденные проверки, blockers, точную следующую задачу и разрешения. Не хранить полный чат вместо краткой сводки. Ссылка на внешнюю сводку полезна, но source task report и требования должны оставаться доступны без капсулы.

## Использование подписок

Приложение не вызывает LLM. Подписки используются разработчиком для подготовки, реализации и review. Локальная агентная работа, API-оркестрация и обычный CI — разные режимы. При запуске CI через API-ключ согласовать billing/лимиты отдельно; не предполагать, что Pro оплачивает любые API-вызовы. [OpenAI pricing](https://learn.chatgpt.com/docs/pricing).

На первом этапе CI — детерминированные проверки без LLM. Агент может объяснять их результаты в своей сессии. Автономная система «агент берёт issue → сам выпускает продукт» не требуется для начального проекта.
