# Spec-Driven Development и работа AI-agents

Workflow принят из прямого указания владельца 2026-10-19; детали продуктового плана остаются Draft. [SPEC](../specs/PRODUCT_SPEC.md), [очередь](../plans/IMPLEMENTATION_PLAN.md), [AGENTS](../../AGENTS.md).

## Цикл изменения — каноническое правило

Решение владельца 2026-10-19; уточнено 2026-10-19: сначала PR, затем review, approve — комментарием-вердиктом. Это единственное каноническое описание цикла; другие документы на него ссылаются. Цикл обязателен для **любого** изменения source-репозитория `project/`, включая документацию, тесты и инструкции агентам. Прямой push в `main` запрещён.

1. **Issue.** У каждого изменения есть issue в MaratGaZa/open-media-cast: цель, scope, критерий приёмки. Существующий issue переиспользуется, новый создаётся до ветки. Одно issue — одна небольшая конечная задача; большие цели сначала разбиваются на несколько issue.
2. **Ветка от актуального `main`.** `git fetch origin` → ветка от `origin/main` с именем `<agent>/<issue>-<slug>`, например `codex/7-readme`. Записать base SHA. Не ветвиться от незамерженной ветки. Несвязанные dirty changes в PR не включать.
3. **Изменение → проверки → commit → push.** Только изменение этой задачи с её тестами и документами. Проверки по типу изменения — [PIPELINE](PIPELINE.md). Commit message ссылается на issue.
4. **PR в `main`.** В описании: `Closes #<issue>`, цель, scope, выполненные проверки с результатом и evidence, что не проверено. Draft PR допустим, пока проверки не готовы.
5. **Review в PR.** Независимый reviewer (другая сессия или модель, либо владелец) по skill [review-change](../../.agents/skills/review-change/SKILL.md) оставляет в PR комментарий-вердикт в формате ниже. Автор изменения не ревьюит своё изменение. Самопроверка автора остаётся в описании PR, но вердиктом не является.
6. **REQUEST CHANGES.** Исправления в той же ветке → затронутые проверки → commit → push → новый вердикт на новый head SHA. Повторять до APPROVE. Замечания, с которыми автор не согласен, обсуждаются в PR; решает владелец.
7. **Merge.** Только если последний вердикт — APPROVE на **текущий** head SHA, обязательные checks зелёные, обязательные замечания закрыты. Любой push после APPROVE его отменяет. После merge проверить, что issue закрылся и `main` содержит изменение; удалить ветку. Следующая зависимая задача начинается с новой ветки от обновлённого `main`.

### Формат вердикта

GitHub не даёт автору PR нажать Approve, а агент работает под аккаунтом владельца. Поэтому approve — это комментарий в PR:

```text
REVIEW: APPROVE            (или REVIEW: REQUEST CHANGES)
Head: <полный SHA head-коммита>
Reviewer: <модель/сессия или владелец>
Checked: <что проверено и чем>
Findings:
- [blocking] <файл:строка> — <проблема и последствие>
- [non-blocking] ...
```

При публикации переданного владельцем внешнего review сохранять автора, SHA, результаты и оговорки reviewer; не представлять их как собственную независимую проверку.

APPROVE допустим только без blocking findings. Вердикт без полного SHA или на устаревший SHA для merge не считается.

### Полномочия и исключения

Поручение задачи по этому циклу включает issue, ветку, commit, push, PR и merge после APPROVE, если в поручении нет ограничения (review-only, local-only, «без merge»); ограничение поручения приоритетно. Цикл не разрешает начинать следующие задачи, принимать Proposed ADR, создавать новые remote или выпускать релизы. Нельзя выдавать собственному изменению вердикт за reviewer или придумывать approve, URL и merge. Если remote, доступ или reviewer недоступны, подготовить проверяемое изменение локально и явно указать, на каком шаге цикл остановлен.

**Капсула — локальное исключение:** ветка от локального `main` → изменение и проверки → локальный commit → review → APPROVE → интеграция в локальный `main`; без issue, remote, push и PR. Source PR и SHA капсулы связываются в локальной сводке.

## Роли и границы

Владелец принимает продуктовые решения и наблюдает реальное устройство. Исследователь проверяет источники и формулирует гипотезы. Исполнитель меняет код. Reviewer оценивает конкретный diff/snapshot. Автор учебного материала объясняет уже проверенный результат и явно обозначает ещё не реализованные примеры.

Это роли в процессе, не требование держать четыре платных агента постоянно. Можно использовать одну модель последовательно; для независимого review дать другой модели/сессии raw diff, требования и результаты без подсказки желаемого вывода. Параллельные изменения допустимы в независимых write scopes с заранее определённой интеграцией.

## Пакет входа агенту

```text
Задача: одна согласованная подзадача E07 по HTTP Range.
Прочитай AGENTS.md, REQ-005, TEST-HTTP-01 и issue этой подзадачи.
Цель: проверить байты/заголовки 206 и 416 на локальном сервере.
До начала подтвердить принятие scope и merge зависимостей.
Далее выполнить канонический цикл выше, начиная с issue и ветки.
Не добавлять discovery, UI или другие протоколы; сохранить evidence.
После PR дождаться независимого вердикта. Следующая задача отдельно.
```

Это пример будущей задачи, не команда выполнить её сейчас. Для других задач сохраняется конкретность входа, границ и evidence; текст не нужно копировать механически.

## Использование подписок

Приложение не вызывает LLM. Подписки используются разработчиком для подготовки, реализации и review. Локальная агентная работа, API-оркестрация и обычный CI — разные режимы. При запуске CI через API-ключ согласовать billing/лимиты отдельно; не предполагать, что Pro оплачивает любые API-вызовы. [OpenAI pricing](https://learn.chatgpt.com/docs/pricing).

На первом этапе CI — детерминированные проверки без LLM. Агент может объяснять их результаты в своей сессии. Автономная система «агент берёт issue → сам выпускает продукт» не требуется для начального проекта.
