# Open Media Cast — контракт разработки

Версия 0.2.0 · 2026-10-19. Workflow небольших задач задан владельцем; принятие стека/дерева и запуск конкретной реализации отдельны.

## Область и источники

Этот файл действует для `project/`. Это самостоятельный source-репозиторий; только он размещается на GitHub в публичном репозитории MaratGaZa/open-media-cast. Внешняя капсула остаётся локальной, её содержимое не включать в push/PR. Перед изменениями проверь его корень и `git status --short`; сохраняй несвязанные изменения пользователя. Инструкции других продуктов не применяются.

Читай по задаче: [SPEC](docs/specs/PRODUCT_SPEC.md), применимые [ADR](docs/adr/ADR-002-APPLICATION-ARCHITECTURE.md), [очередь](docs/plans/IMPLEMENTATION_PLAN.md), [тестирование](docs/testing/TEST_STRATEGY.md). SPEC описывает намерение, код и runtime evidence доказывают реализацию. Proposed ADR не равен принятому решению.

## Работа

1. Получи конкретную задачу или выбери её в рамках уже разрешённого пользователем объёма. Для `take next step` действует первая готовая execution task очереди; при Draft-плане сначала требуется принятие соответствующего объёма.
2. Требование/изменение контракта сначала отрази в SPEC и критериях, затем в плане и коде. Ссылки `REQ-* → TEST-* → evidence` должны оставаться проверяемыми.
3. Новое поведение разрабатывай test-first: тест → подтверждённый RED → минимальная реализация → GREEN; [правила и первые задачи](docs/runbooks/TEST_FIRST.md). Ошибка окружения не является RED. Одна конечная задача — один небольшой проверяемый результат и PR; группы плана сначала разделяй. Меняй минимальный связный объём. Независимые платформы — модули; не копируй core между ними. Новые каталоги согласовывай согласно просьбе владельца. Принятие конкретного дерева применимого ADR разрешает только перечисленные каталоги; пока ADR Proposed, разрешение не предполагается.
4. Не называй поддержкой устройства наличие библиотеки, mock или успешную сборку. Статусы и уровни доказательств заданы в TEST_STRATEGY.
5. Применяй [engineering rules](docs/rules/ENGINEERING_RULES.md). Пользовательское медиа не загружай во внешние AI-сервисы; для fixture используй синтетические данные.
6. Перечисляй фактически запущенные проверки и ограничения. Продуктовые проверки для ещё не созданного кода обозначай not applicable, а не passed.

## Цикл изменения — обязателен

Любое изменение этого репозитория, включая документацию, проходит цикл. Полное правило и формат вердикта — [SDD](docs/runbooks/SDD_AND_AGENTS.md#цикл-изменения--каноническое-правило).

Обычная правка текста не запускает все skills. Skills не дают разрешения на дополнительные внешние действия. Их структура соответствует SKILL.md; совместимость обнаружения с каждым используемым AI-agent проверяется отдельно.

Общий `evolve-ai-instructions` используй, если доступен по локальной ссылке; это необязательная зависимость окружения, не prerequisite обычной задачи или CI. Установка/переносимость и статус проверки набора — в [SKILLS.md](docs/runbooks/SKILLS.md).

Для разработки запускай агента из `project/`. Claude Code получает тот же контракт через `CLAUDE.md` и тот же набор через `.claude/skills`; канонические файлы остаются в `.agents/skills`. Префикс ветки — соглашение инструмента, а не зависимость кода от провайдера.

## Проверки по типу изменения

- Документация: локальные ссылки, непротиворечивость статусов, отсутствие фиктивного runtime evidence.
- После появления Rust: fmt, clippy с warnings-as-errors, применимые unit/integration tests; точные команды хранятся в pipeline runbook и manifests.
- После появления UI: typecheck, lint, тесты поведения, сборка целевой платформы.
- Протокол/медиа: контрактные тесты плюс реальное устройство для затронутого поведения; заранее ограничить время и тестовый файл.
- Packaging: установка и запуск собранного артефакта на целевой системе, очистка временных ресурсов.

## Полномочия и завершение

Поручение конкретной задачи включает весь цикл изменения, от issue до merge после APPROVE текущего head SHA. Local-only, review-only или иное явное ограничение поручения приоритетно. Нельзя автоматически создавать неизвестный remote, принимать Proposed стек, начинать следующую задачу, публиковать release, создавать платный ресурс или менять роутер/firewall. Используй уже выданные разрешения; не запрашивай их повторно без причины. При отсутствии remote/reviewer подготовь локальный результат и укажи незавершённую внешнюю часть цикла.

Для review фиксируй SHA при наличии коммита, иначе точно описывай snapshot и незакоммиченные изменения. Отчёт задачи должен быть доступен в source-репозитории/PR; внешние session artifacts добавляют учебный контекст, но не являются единственным доказательством. Исторические записи не переписывай.
