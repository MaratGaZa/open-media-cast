# Review изменения

Пути ниже указаны от корня `project/`. Определи объект review: диапазон коммитов, рабочие изменения или перечисленный snapshot файлов. Проверь Git root и status. Если коммитов ещё нет, включи новые untracked-файлы: пустой `git diff` не означает отсутствие изменений. Не создавай коммит только ради review.

Прочитай относящиеся к изменению REQ, ADR и `docs/rules/ENGINEERING_RULES.md`. Для branch review зафиксируй сравниваемые ревизии; для рабочего дерева — перечень и хеши проверенных файлов, когда нужен воспроизводимый snapshot. Не подменяй запрошенный диапазон автоматически выбранным merge-base.

Проверь два направления:

- **Требования:** что реализовано, пропущено, сделано сверх поручения или противоречит принятым решениям. Draft-идея не становится обязательным критерием без принятия соответствующего объёма.
- **Корректность:** реальные ошибки, нарушенные контракты и затронутые риски. Для медиасессии важны отмена/Stop, устаревшие события после seek, доступность URL с приёмника, Range, жизненный цикл encoder и очистка ресурсов. Проверяй только относящееся к diff.

Каждый finding связывай со сценарием, местом и последствием. Отделяй дефект от предпочтения стиля и от недостающей проверки. Не требуй абстракций только ради устранения внешне похожего кода. Не называй потенциальную проблему подтверждённой без достаточного основания.

Проверь качество evidence: тест публичного поведения должен обнаруживать ошибку, а mock приёмника не доказывает работу телевизора. Не считай сборку доказательством установки на минимальную ОС. При нехватке устройства укажи конкретный пробел, сохраняя полезные выводы о локальном коде.

Review по умолчанию выдаёт замечания без исправления файлов. Если пользователь поручил также исправления, выполни их в этом объёме и отдели выводы до/после. Самопроверку называй самопроверкой. Независимое review существует только после фактического отдельного рассмотрения; несколько заголовков одного автора не создают независимость.

Итог: объект и границы review, findings по влиянию с путём/строкой или разделом, выполненные проверки и ограничения. При отсутствии findings укажи, что именно проверено. Для release verdict используй `review-release-readiness`; review само по себе не разрешает merge, push или публикацию комментария.
