# Планирование изменения

Пути ниже указаны от корня репозитория `project/`. Прочитай `AGENTS.md`, затронутые разделы `docs/specs/PRODUCT_SPEC.md`, применимые ADR и `docs/plans/IMPLEMENTATION_PLAN.md`. Проверяй наличие реализации перед выводами о её поведении.

Сначала установи пользовательский результат, уже принятые решения и оставшиеся неизвестные. Сохраняй три семейства приёмников в v1 и согласованный порядок платформ. Не принимай Proposed стек за обязательный. Уточняй только то, без чего меняется результат или нельзя продолжить зависимую работу; разрешённую независимую часть выполняй.

Для изменения поведения предложи наблюдаемые критерии и обновление REQ. Для задачи без изменения поведения достаточно ссылки на существующий критерий. Не создавай второй SPEC или параллельную очередь `tasks/todo.md`. Технические альтернативы фиксируй в ADR, а не превращай случайный выбор библиотеки в требование продукта.

Разделяй работу по проверяемым результатам: например, discovery одного протокола, воспроизведение fixture и управление сессией. Риск совместимости проверяй ранним экспериментом. Число файлов само по себе не определяет размер задачи; изменение общего контракта и его клиентов может быть одним связным результатом.

Каждая задача содержит: цель, REQ, зависимости, границы изменения, критерии приёмки, способ проверки и необходимый уровень evidence из `docs/testing/TEST_STRATEGY.md`. Для ещё отсутствующей инфраструктуры укажи prerequisite вместо выдуманной команды. Пример плана теста не является выполненным тестом.

Параллелизм предлагай только для независимых областей записи после согласования общего контракта. Роли исследователя, исполнителя и reviewer не требуют отдельных процессов. Запуск агентов зависит от доступных средств и разрешённого объёма, а публикация не является обязательным завершением планирования.

Сохраняй предложения в существующих `docs/specs/`, `docs/plans/`, `docs/adr/`. Новые категории каталогов согласовывай по просьбе владельца. Покажи конкретный план, список решений и первую готовую задачу. Не запрашивай повторное согласование уже разрешённого объёма; подготовка плана не запускает автоматически весь roadmap.
